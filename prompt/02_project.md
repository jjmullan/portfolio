## 기술 경험

### 1. 수동 수집 프로세스를 99% 자동화하여 작업 시간 79% 단축

#### 상황 (Situation)

- 상영 정보의 특성상 최신화된 데이터를 수시로 업데이트해야 하는 애로사항 존재
- 데이터 수집 후 영화진흥위원회 코드 검증, Database Row 확인 과정 등 부수적인 업무들이 존재 → 비정확성 문제로 신뢰도 저하 우려

#### 과제 (Task)

- 개별 수집 과정을 일원화하고, 부수적인 업무를 통합하는 자동화 프로세스 구축

#### 행동 (Action)

- 예매처별 데이터 렌더링 방식에 맞는 웹 스크래핑 기술 구현 (Headless 브라우저 사용 대신 fetch() 를 직접 요청하는 방식으로 구현)
- 수집한 데이터를 Database 의 테이블 구조에 맞게 정제・정규화하고, 기존 테이블의 유니크 제약조건을 검증하여 중복된 데이터는 updated_at 만 now() 로 갱신하도록 구현
- Kobis API 를 호출하여 영화명, 러닝타임, 관람등급 데이터와 매핑되는 데이터가 존재하는 경우 코드를 자동 수집하는 과정을 추가
- Vercel Cron 을 활용하여 일원화된 작업을 특정 UTC 시간마다 실행하는 자동화된 파이프라인 구축

#### 결과 (Result)

- 데이터 수집 과정 및 부수 작업을 99% 자동화하며 반복 작업 시간을 79% 단축시켰고, API 호출 응답의 구조화된 컬럼 데이터를 수집하여 데이터의 오류 및 비정확성 문제를 해소
- 현재 디트릭스 예매 채널 자동 수집 시 500 Internal Server Error 가 응답되는 문제 → curl 명령어로 해당 채널의 데이터를 수동 수집하고 있으며 추후 개선하고자 함

### 2. 분 단위 전역 시간 동기화로 메모리 누수 및 불필요한 리렌더링 방지

#### 상황 (Situation)

- 서비스 주요 화면에서 사용되는 현재 시간 상태 코드를 컴포넌트마다 중복 정의하면서 렌더링 성능 저하 발생

#### 과제 (Task)

- 렌더링 비용을 최소화할 수 있는 상태 관리 전략 도입

#### 행동 (Action)

- 현재 시각을 1분 단위로 갱신하여 상태로 공급하고, 필요한 컴포넌트에서 구독하여 사용하는 형태로 개선
- 최초 렌더링 시 즉시 현재 시간을 반영하고, 이후에는 setTimeout 과 setInterval 을 조합하여 매 분 정각에 가까운 시점에 상태가 갱신되도록 구현

#### 결과 (Result)

- 전역 시간 상태를 단일 Provider 에서 관리하도록 개선하여 중복 타이머 생성 및 불필요한 리렌더링 방지
- setTimeout 과 setInterval 의 실행 및 해제 시점을 효과적으로 관리하여 메모리 누수 가능성 최소화

### 3. 페이지별 렌더링 방식 최적화로 데이터 조회 성능 및 SEO 향상

#### 상황 (Situation)

- 주요 페이지의 초기 데이터 로딩을 Client Component 와 Tanstack Query 훅에서 시작하는 구조 → 데이터 조회 속도와 SEO 를 고려한 렌더링 방식 도입 필요

#### 과제 (Task)

- 데이터 갱신 주기와 SEO 를 고려한 SSR 또는 SSG 렌더링 방식 도입 고려

#### 행동 (Action)

- 홈: 서버 데이터 요청과 페이지 렌더링 이후 Hydration 요소를 분리하는 Server Component Shell + CSR 혼합 방식 채택
- 영화 목록: 대량의 데이터, 페이지네이션, 정렬 등 클라이언트 상호작용이 많은 화면으로 CSR 방식 채택
- 영화 상세페이지: 데이터 변경이 매우 적고 초기 진입 시 핵심 데이터 노출이 중요하다는 점을 고려하여 SSR 방식 채택
- 상영시간표: 사용자 상호작용이 많은 본문은 CSR 로 유지하면서 검색 노출에 필요한 상영 정보 요약과 JSON-LD 만 부분 SSR 로 도입

#### 결과 (Result)

- 주요 페이지별 데이터 특성과 상호작용 의존도를 기준으로 렌더링 전략을 재정의하여 데이터 조회 속도 최대 92% 상승 (홈 화면)
- 검색엔진이 상영시간표를 단순 텍스트가 아닌 영화 상영 이벤트로 해석할 수 있도록 JSON-LD 구조화 데이터를 제공하여 초기 HTML 단계의 콘텐츠 이해도와 SEO 노출 안정성 향상

### 4. RPC 기반 범위 조회 및 렌더링 방식 변경으로 체감 응답 시간 43% 개선

#### 상황 (Situation)

- 상영시간표 화면은 영화, 극장, 상영관, 기획전 등 여러 엔티티가 조합된 데이터를 제공해야 하는 구조로, 다중 Join 및 View 기반 조회를 사용하면서 과도한 Payload 응답이 발생

#### 과제 (Task)

- 필요한 데이터만 조회하도록 요청 구조를 개선하여 응답 시간을 줄이는 것

#### 행동 (Action)

- 전체 상영 데이터 요청 후 클라이언트에서 날짜/시간 옵션을 추출하고 상영 데이터를 필터링하던 방식 → 날짜/시간 필터 조회 RPC 와 상영 목록 조회 RPC 를 병렬로 실행하도록 개선
- 기존 View 기반 조회 방식과 RPC 기반 조회 방식을 교차 실행하여 실제 체감 성능 측정

#### 결과 (Result)

- RPC 기반 조회로 Payload 가 약 84% 감소(849,288 bytes → 132,478 bytes)하였고, 화면 첫 진입 기준 병렬 요청 체감 응답 시간이 약 43%(158 ms → 89.64ms) 개선됨

### 5. 백오피스 환경을 구축하여 운영효율성 증가

#### 상황 (Situation)

- 자동 수집 데이터와 수동 보정된 데이터가 함께 존재하기 때문에, 운영자가 데이터를 쉽게 확인·수정할 수 있는 관리 페이지가 필요

#### 과제 (Task)

- 운영자가 코드나 DB에 직접 접근하지 않고도 서비스 노출 데이터를 생성·수정·삭제할 수 있는 구조 마련

#### 행동 (Action)

- 백오피스 라우트 구성 및 관리자 전용 화면 분리 → 서비스는 모바일 UI 중심으로 제공하나, 백오피스는 웹 UI 중심으로 제공
- Access Token Cookie 기반 보호 로직 구성 → 인증된 운영자만 백오피스 페이지와 내부 데이터 관리 API에 접근할 수 있도록 처리
- 도메인별 목록 조회, 데이터 생성 및 수정 기능 구현
- 목록 화면 내 페이지네이션, 검색, 정렬 기능을 적용하여 대량 데이터 관리 시 탐색 비용 감소

#### 결과 (Result)

- Database 에 직접 접근하지 않고도 서비스 주요 데이터를 관리할 수 있는 운영효율적인 백오피스 환경 구축

### 6. 검색 유입 분석과 사용자 행동 추적을 위한 운영 지표 기반 구축

#### 상황 (Situation)

- 서비스 배포 이후 서비스 유입 활성화 및 실제 유입 경로, 검색 노출 상태, 사용자 행동 데이터를 확인할 수 있는 운영 지표 기반 마련

#### 과제 (Task)

- Google Search Console, Naver SearchAdvisor, Amplitude 연동
- 검색엔진 크롤링 경로와 페이지 색인 가능성 개선

#### 행동 (Action)

- Google Search Console 과 Naver SearchAdvisor 를 연동하여 소유권 검증 및 검색엔진 크롤링 및 색인 상태 추적
- robots.txt 를 통해 검색엔진 접근 정책을 정의하고, sitemap.xml 로 주요 정적 페이지와 상세 페이지 URL 구조 제공
- Amplitude를 연동해 주요 사용자 행동 이벤트를 추적할 수 있는 분석 기반 구성

#### 결과 (Result)

- 검색엔진 인덱싱 최적화를 통한 Organic Search 유입 기대, 주요 행동 데이터를 추적할 수 있는 분석 기반 확보

# 2. AI 포트폴리오

## 개요

- **구분**: 개인
- **기간**: 2026. 2. 18 ~ 2026. 3. 5
- **기술 스택**
  - **프레임워크**: TypeScript, React.js 19, Next.js 16
  - **AI Agent**: @anthropic-ai/sdk, Claude Code
  - **상태 관리**: Zustand
  - **백엔드**: Supabase

  - **기타**: Next/third-parties(Google Analytics)

  서비스: https://youngjune.dev/
- 설명
  사용자의 질문 의도를 기반으로 분산된 포트폴리오 정보를 통합 참조하여 응답하는 AI Native 포트폴리오

## 기획 의도

타겟 사용자인 채용 담당자가 포트폴리오 페이지 전체를 일일이 탐색하는 과정에서 높은 피로감을 느낄 것이라 판단했습니다. 이를 개선하고자 지원자의 핵심 역량을 쉽고 빠르고 정확하게 전달하기 위한 방법으로 AI 에이전트를 활용한 Q&A 서비스 ‘AI 포트폴리오’를 기획하게 되었습니다.

## 기술 경험

### 1. 요구사항에 맞는 데이터베이스 설계 및 스트리밍 응답 프로세스 구현

#### 상황 (Situation)

- 핵심 비즈니스 모델인 AI 스트리밍 응답 과정에 대해 이해하고 최적화된 방식으로 기술을 구현해야 하는 상황

#### 과제 (Task)

- 비즈니스 요구사항에 맞는 데이터베이스 설계 및 기능 구현

#### 행동 (Action)

- Anthropic SDK 와 Next.js Route Handler 를 결합하여 AI 응답을 청크 단위로 클라이언트에 전달하는 스트리밍 파이프라인을 구축하고, 스트리밍 중 Fallback UI 제공
- 입력된 프롬프트에서 추출한 제목 데이터와 입・출력 본문 데이터를 분리 저장하고 외래키 제약 조건으로 연결하는데이터베이스 구조를 설계

#### 결과 (Result)

- 청크 단위 렌더링 방식을 통해 초기 응답 속도 및 화면 전환 경험을 대폭 개선하고 응답 데이터의 정합성을 보장할 수 있는 데이터베이스 구조 마련

### 2. AI 모델 최적화로 토큰 비용 27% 감소

#### 상황 (Situation)

- 타입스크립트 파일 내 백틱 문자열로 대용량 컨텍스트를 로드하여 전송 → 회당 15,950 Input 토큰에 달하는 컨텍스트가 매 요청마다 갱신 및 전송되어 토큰 소모가 누적됨

#### 과제 (Task)

- 컨텍스트의 재사용성을 높이고 불필요한 중복 전송을 방지하는 비용 효율적인 토큰 소비 구조 마련

#### 행동 (Action)

- 타입스크립트 파일에서 독립된 마크다운 파일로 교체하고, 컨텍스트를 전송하는 시스템 프롬프트에 캐싱 마커를 적용하여 동일 컨텍스트 요청을 API 캐시에서 처리하도록 개선
- 시스템 프롬프트의 Prefix 에 환각 현상을 구조적으로 방지할 수 있는 항목을 추가하여 응답 범위를 명확히 제어함으로써 응답 제어 구조를 강화
- 요구 스펙 대비 오버스펙이었던 Sonnet 4.5 모델 대신, 응답 지연 시간이 짧고 가성비가 높은 Haiku 4.5 모델로 전환

#### 결과 (Result)

- 토큰 사용량이 2.4배 증가했지만 오히려 토큰 비용이 27% 감소($1.27 → $0.92)하고 실효 단가가 79% 하락($0.00268/1K → $0.00056/1K)하며 비용 효율적인 사용 구조 마련

### 3. 권한 검증 구조 개선을 통한 링크 공유 UX 확보

#### 상황 (Situation)

- RLS 설정 문제로 다른 사람의 대화 내역을 링크로 공유하거나 소유자의 다른 기기에서 다시 열 수 없는 문제

#### 과제 (Task)

- 권한 검증 문제를 해소하여 링크 공유가 가능하도록 개선

#### 행동 (Action)

- SELECT RLS 설정을 공개 조회가 가능하도록 수정하고, 소유자 세션 여부를 검증하여 소유자에게만 프롬프트 입력 UI 와 INSERT 권한을 제공하도록 재설계

#### 결과 (Result)

- 대화 내역을 링크로 공유할 수 있는 UX를 구현하여 포트폴리오 서비스 접근성을 높이고 사용성을 개선

### 4. 서버 트리거 함수 기반 데이터 원자성 및 정합성 확보

#### 상황 (Situation)

- 프롬프트 원본 데이터를 보관하는 테이블(context)에 새로운 데이터가 추가될 때, 관계된 부모 테이블의 최종 수정 시간(updated_at)을 동기화할 수 없는 문제

#### 과제 (Task)

- 자식 테이블의 데이터 변경 이벤트와 부모 테이블의 컬럼을 갱신하는 방법 마련

#### 행동 (Action)

- 처음에는 클라이언트에서 비동기로 처리하는 방식으로 구현하였으나, api 요청 오류 시 데이터 원자성 및 정합성 문제 발생 가능성으로 롤백
- 서버에서 자식 테이블에 INSERT 이벤트가 발생할 때, 외래 키로 연결된 부모 테이블 row 의 updated_at 컬럼 값을 now()로 자동 갱신하는 데이터베이스 트리거 및 함수 구현

#### 결과 (Result)

- 트랜잭션 불일치 문제를 해소하여 데이터의 원자성과 정합성을 확보하고 api 호출 빈도를 줄여 렌더링 성능을 높임

### 5. MCP 기반 개발 워크플로우 통합으로 개발 생산성 향상

#### 상황 (Situation)

## 기술 경험

### 1. 사용자의 서비스 여정을 고려한 지도 탐색 UX 제공

#### 상황 (Situation)

- 지금 내 주변에 무엇이 있는지 빠르게 탐색하여 이동할 수 있는 즉시성 높은 탐색 경험 필요

#### 과제 (Task)

- 타겟 사용자의 서비스 이용 흐름을 고려한 지도 탐색 경험 설계

#### 행동 (Action)

- Kakao Map SDK 와 Geolocation API 를 활용하여 서비스 세션 최초 로드 시 위치 정보 수집 요청 → 현재 위치 버튼을 클릭하면 위치를 재수집하도록 설계
- 무분별한 데이터 생성을 방지하기 위해 현재 위치에서 3km 이상 떨어진 경우 위치 생성을 제한
- 지도 중심 좌표(lat, lng)를 URL QueryString 으로 동기화 → 히스토리 이동 시에도 이전 탐색 흐름을 유지하도록 개선
- 즐겨찾기, 리뷰, 제품 카테고리 등을 지도에 표기하여 탐색 과정에서 자연스럽게 주요 데이터를 획득하는 흐름 제공
- 단계별 클러스터링을 도입하여 대용량 데이터의 렌더링 부하를 방지

#### 결과 (Result)

- 지도 탐색, 정보 수집, 위치 생성 등 핵심 기능이 사용자 흐름 안에서 자연스럽게 연결되는 향상된 UX 를 제공

### 2. 쿼리 키 팩토리 기반 서버 상태 관리 전략으로 데이터 동기화 개선

#### 상황 (Situation)

- 여러 도메인의 서버 데이터가 동시에 주입됨에 따라, 도메인별 서버 상태를 일관된 기준으로 식별하고 데이터 변경 시 어떤 캐시를 갱신해야 하는지 추적 가능할 수 있는 구조 필요

#### 과제 (Task)

- 도메인과 조회 조건 기준으로 관리할 수 있는 쿼리 키 체계를 설계

#### 행동 (Action)

- 쿼리 키 객체를 도메인별로 구조화하고, 조회 조건에 따라 쿼리 키를 생성하는 쿼리 키 팩토리 패턴을 도입
- 배열 상수를 먼저 정의하여 캐시를 계층적으로 식별하고 필요한 범위의 캐시를 쉽게 갱신
- 쿼리 키가 적용되는 커스텀 훅을 별도 파일로 분리하고 도메인별 entities, features 레이어로 이동
- 서비스 체류 시간을 고려한 staleTime, gcTime, refetchOnWindowFocus 설정

#### 결과 (Result)

- 같은 데이터를 여러 화면에서 사용하더라도 일관된 방식으로 조회하고 갱신할 수 있는 체계적인 서버 상태 관리 전략 마련
- 동일 데이터를 여러 컴포넌트에서 구독해도 중복 네트워크 요청 없이 캐시를 공유하여 불필요한 API 요청을 감소

### 3. 확장 가능한 도메인별 접근 제어 구조 도입

#### 상황 (Situation)

- 사용자 세션 인증 여부가 여러 화면에 걸쳐 함께 존재하면서 인증 흐름을 일관되게 관리해야 할 필요성

#### 과제 (Task)

- React Router 기반 CSR 구조에서 세션 로드, 인증 가드, 도메인별 라우팅 책임을 분리

#### 행동 (Action)

- Supabase Auth 의 onAuthStateChange 를 세션 Provider 에서 구독하여 로그인 세션을 전역에서 관리
- 도메인별 라우트 파일을 독립적으로 관리하여 인증이 필요한 영역과 비인증 사용자 중심 영역을 명확히 분리
- 도메인 라우트 경로를 Global → 도메인 → 페이지 컴포넌트 Layout 계층으로 구조화하고, 도메인 레벨에서 로그인 상태를 공급하여 검증하도록 구현

#### 결과 (Result)

- 신규 기능이 추가될 때 라우트와 인증 정책을 해당 도메인 Layout 에 연결하는 방식으로 확장할 수 있게 되어 신규 도메인에 유연하게 대처 가능
- 인증 조건을 Layout 에서 일관되게 관리하고 페이지는 화면 렌더링과 도메인 기능 구현에 집중하는 명확한 책임 구조 마련

### 4. 데이터 정합성을 고려한 테이블 구조 설계

#### 상황 (Situation)

- 서비스의 핵심 비즈니스 모델의 효율적이고 효과적인 관리를 위한 체계적인 데이터베이스 구조 설계 필요

#### 과제 (Task)

- 기능 변경에 유연하게 대처할 수 있는 정규화된 데이터베이스 모델링

#### 행동 (Action)

- 데이터베이스 구현 전 ERD 설계에 충분히 많은 시간을 할애하여 주요 엔티티의 속성을 도출
- 테이블 정의서, 용어 사전을 작성하고 동기화하여 프로젝트 종료 시까지 살아있는 문서로 활용

#### 결과 (Result)

- 초기 설계에 대한 고민과 분석의 중요성을 체감, 구조적이고 체계적인 설계가 서비스 안정성과 확장성의 기반이 된다는 것을 깨달음

### 5. BFF 구조 재설계로 서비스 요구사항 최적화

#### 상황 (Situation)

- 사용자 인증과 DB 변경의 책임이 클라이언트에 치중되어 있는 문제 → BFF 를 도입하여 서버 측 검증으로 전환하고 분산되어 있던 API 호출 로직을 통합하여 코드량을 80% 감소시킴
- 단순 SELECT 요청에서도 응답 속도가 저하되는 문제가 발생 → 실시간 위치 정보를 제공해야 하는 서비스의 특성상 잦은 레이턴시 발생은 사용자의 경험을 해침

#### 결과 (Result)

- 클라이언트는 인증 토큰 전달과 요청 호출만 담당하고 민감한 쓰기 기능과 비즈니스 처리 로직을 서버로 격리하여 인증, 보안, 책임 분리가 명확한 API 흐름을 구성
- 모든 요청을 서버로 통합하는 구조보다 서비스의 특성과 요구사항에 맞는 아키텍처 설계의 중요성을 깨달음
