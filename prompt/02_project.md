# 1. AI 포트폴리오

## 개요

- **구분**: 개인
- **기간**: 2026. 2. 18 ~ 2026. 3. 5
- **기술 스택**
  - **프레임워크**: TypeScript, React.js 19, Next.js 16
  - **AI Agent**: @anthropic-ai/sdk, Claude Code, Codex
  - **상태 관리**: Zustand
  - **백엔드**: Supabase
  - **유틸리티**: Next/third-parties(Google Analytics), Tailwind CSS, Shadcn, , Biome
  - **도구**: Cursor, Notion, Slack, Figma
  - **배포**: Vercel
- 링크
  서비스: https://youngjune.dev/
- 설명
  학습된 컨텍스트를 기반으로 맞춤형 정보를 실시간으로 스트리밍하여 전달하는 것이 특징인 **AI Agent 포트폴리오**

## 개발 배경

- 상황
  주요 사용자인 채용 담당자와 현업 개발자는 원하는 정보를 얻기 위해 직접 탐색해야 하는 구조 → 높은 탐색 비용이 발생함, 피로도 증가
- 액션
  사용자에게 친숙한 기존 AI 서비스의 UI를 참고한 챗봇형 Q&A 서비스를 개발
  사용자는 원하는 정보를 직접 질문하고, AI는 학습된 컨텍스트 기반의 스트리밍 응답을 제공하여 즉시 확인할 수 있도록 구현
- 결과
  기존의 수동적인 탐색 방식을 능동적인 방식으로 전환하여 사용자의 탐색 비용 절감 및 사용자 친화적 경험을 제공

## 기술 경험

### 1. Claude AI SDK 기반 스트리밍 응답 구현

- 상황
  AI가 응답을 완성할 때까지 대기하게 된다면 사용자는 현재 진행 상황을 알지 못해 오류로 파악할 수 있어 사용자 경험을 저해
- 액션
  Anthropic SDK 와 Next.js Route Handler 를 결합하여 AI 응답을 청크 단위로 클라이언트에 전달하는 스트리밍 파이프라인을 구축, 대화형 UI 및 대기 중 커서 애니메이션 제공
- 결과
  사용자가 현재 대화 상태가 어떻게 진행되고 있는지 즉시 인식할 수 있게 되면서 사용자 경험을 향상

- 상황
  기존에는 TypeScript 파일에 정의된 컨텍스트를 로드하는 방식으로, 해당 파일의 최신 변경 이력이 레포지토리에 업데이트가 되어 있어야 했음
- 액션
  컨텍스트를 MD 파일로 교체, API 요청 시 코드 변경 및 재배포 없이 컨텍스트 파일을 서버에서 즉시 로드하여 반영하는 ‘server-only’ 파일로 변경
- 결과
  콘텐츠를 로드할 때마다 서버에서 최신 업데이트된 MD 파일을 로드하여 캐싱과 함께 전달하여 코드 로직과 콘텐츠 파일을 분리

### 2. MCP 기반 AI 개발 워크플로우 자동화

- 상황
  코드·문서·DB·배포가 각각 다른 도구에 분산되어 작업마다 컨텍스트 전환 비용이 반복적으로 발생
- 액션
  Cursor IDE 에 Claude Code 를 설치, Notion, Github, Vercel, Supabase MCP 를 연결
- 결과
  자연어만으로 손쉽게 각 기능을 통합, 중앙제어할 수 있게 되면서 컨텍스트 전환 비용 감소 및 업무 효율 증가

### 3. 서비스 특성에 맞는 AI 최적화로 토큰 비용 절감 및 프롬프트 최적화

- 상황
  정해진 컨텍스트 범위 안에서 유사한 질문을 응답하는 구조이기에, 최고 성능 모델이 아닌 최적의 성능 모델이 필요하다고 판단
  회당 15,950 토큰을 소비하는 동일한 전역 컨텍스트를 매 요청마다 새로 전송하면서 비용이 불필요하게 발생
- 액션
  Sonnet 4.5 모델에 비해 응답 지연 시간이 가장 빠르고 비용 효율적인 Haiku 4.5 모델로 다운그레이드
  전역 컨텍스트를 전송하는 시스템 프롬프트에 캐싱 마커를 적용하여 동일한 프롬프트 요청을 캐시에서 처리
- 결과
  최적화 전과 비교하여 토큰 사용량이 2.4배 증가(Input 473,285 → 1,151,721, Output 34,598 → 47,743)했는데, 오히려 토큰 비용 27% 감소($1.27 → $0.92)하면서 실효 단가가 79% 하락($0.00268/1K → $0.00056/1K)하여 비용효율적인 AI 사용 구조 완성

- 상황
  개인 경험에 맞는 정보를 응답하도록 구현하는 과정에서 AI가 실제 경험과 일치하지 않는 성과를 생성하는 환각 현상이 발생하는 것을 인지
- 액션
  경험에 기반한 정보만 응답하도록 시스템 프롬프트의 프리픽스에 환각 현상을 구조적으로 방지하는 유의사항을 추가하여 제어 구조를 강화
  이력서·프로젝트·기술 경험을 템플릿 단위로 구조화하여 응답 범위를 명확히 제한
- 결과
  경험과 일치하지 않는 응답 발생을 크게 줄이고, 사용자 질문에 대해 일관된 맞춤형 정보를 제공할 수 있는 AI 응답 구조를 구축

### 4. 권한 검증 구조 개선을 통한 링크 공유 UX 확보

- 상황
  Database SELECT 권한을 페이지 진입 시점에 검증하는 구조로 인해 다른 사람의 대화 내역을 링크로 공유하거나 다른 기기에서 다시 열 수 없는 문제
- 액션
  권한 검증 없이 SELECT 를 허용하여 대화 내용을 조회할 수 있도록 하고, 소유자 세션 여부를 검증하여 소유자에게만 프롬프트 입력 UI와 INSERT 권한을 제공하도록 재설계
- 결과
  대화 내역을 링크로 공유할 수 있는 UX를 구현하여 포트폴리오 서비스 접근성과 사용성을 개선

### 5. 트리거 기반 자동 갱신 구조 설계를 통한 데이터 정합성 확보

- 상황
  Supabase 의 Anon 키 환경에서의 제약으로 단일 컬럼(updated_at)을 대상으로 하는 갱신이 허용되지 않아 데이터 변경 이력을 정확히 반영하지 못하는 문제
- 액션
  자식 테이블에 INSERT 가 발생할 때 외래 키로 연결된 부모 테이블 레코드의 updated_at 값을 now()로 자동 갱신하는 트리거를 구현
- 결과
  클라이언트 의존성을 제거하고 데이터 변경 이력의 신뢰성을 확보

- **상황**:

# 2. 포장맛차

## 개요

- **구분**: 개인
- **기간**: 2025. 11. 25 ~ 2025. 2. 27 (139시간)
- **기술 스택**:
  - **프레임워크**: TypeScript, React.js 19
  - **AI Agent**: Claude Code
  - **상태 관리**: Zustand
  - **백엔드**: Supabase
  - **유틸리티**: Tailwind CSS, Shadcn, Biome, @vercel/node
  - **도구**: Cursor, Notion
  - **배포**: Vercel
- 링크
  서비스: https://deliciousstreetfood.vercel.app/
  Github: https://github.com/jjmullan/delicious_street_food
  Notion: https://choiyoungjune.notion.site/2b521bc2456c80ba8a8ef4843c6a68c8?pvs=74
- 설명
  사용자가 직접 위치를 등록하고, 리뷰를 작성하고, 작성된 리뷰를 기반으로 정보를 얻는 것이 특징인 **실시간 길거리 포장마차 위치 탐색 및 공유 서비스**

## 개발 배경

- 상황
  시즌에 따라 유동적으로 운영하는 길거리 포장마차 특성상 사용자의 개인 경험 및 후기에 의존
  유사 서비스(가슴속3천원, 당근 붕어빵지도)의 데이터 불일치, 카테고리 부족 문제
- 액션
  실시간 위치를 추적하여 사용자 주변의 길거리 포장마차 위치를 확인하고, 리뷰를 작성하고, 위치 정보가 없다면 별도의 검토 과정 없이 즉시 생성할 수 있는 지도 서비스 기획
  데이터 불일치 문제를 해결하기 위해 운영 시간과 판매 상품 종류, 가격 등 매장별 정보는 사용자가 작성한 리뷰를 기반으로 추출하도록 개발
- 결과
  위치·가격·운영시간을 실시간으로 공유하는 길거리 음식 특화 지도 서비스 포장맛차를 개발

## 기술 경험

### 1. Kakao Map SDK 기반 위치 데이터 동기화 기능 구현

- 상황
  효율적인 비용으로 운영이 가능하며, 국내 사용자에게 친숙한 지도 API 도입 필요
- 액션
  Google Maps, Naver Map 대비 비용 효율적이며 서비스 요구사항을 만족시키는 최소한의 기능이 포함된 Kakao Map SDK 를 기술 스택으로 선정
  Geolocation API 와 Context + Provider 패턴을 결합하여 위치 권한 요청 → 좌표 수신 → 전역 상태 갱신의 흐름을 단일 Provider로 응집
  하버사인 공식을 기반으로 현재 위치와의 거리를 검증하여 좌표 조작을 통한 비정상 데이터 등록을 방지
  지도 중심 좌표(lat, lng)를 URL 쿼리 스트링으로 직렬화
  줌 레벨에 따라 인접 마커를 동적으로 클러스터링 적용
- 결과
  비용 효율적이고 신뢰성 있는 위치 기반 서비스 환경을 구축

### 2. Tanstack Query 기반 서버 상태 관리 및 페이지 구조 설계

- 상황
  카카오맵, 위치 상세, 유저 프로필, 후기 작성, 인증 페이지 등 다양한 도메인 페이지가 공존하는 구조로, 도메인 경계를 명확히하고 라우트 간 충돌 가능성을 배제할 필요성
- 액션
  도메인별로 라우트 파일을 분리, 각 도메인 라우트를 GlobalLayout → 도메인별 Layout → 페이지 컴포넌트 계층으로 구조화
  도메인별 Layout 레벨에서 전역 상태를 관리하여 컴포넌트에 Props 로 전달하는 구조로 전역 상태 최소화, 로그인 유무 검증 후 리다이렉트하는 역방향 가드 등을 설계
- 결과
  도메인별 라우트 파일을 독립적으로 관리하게 되면서 신규 도메인에 유연한 구조를 마련
  인증 가드 로직이 도메인 Layout 로 집중시켜 컴포넌트는 순수 UI 렌더링에 집중이 가능하도록 하여 UI 재사용성 확보

- 상황
  여러 도메인의 서버 상태를 관리해야 하는 구조에서 쿼리 키가 문자열 배열로 분산되면 오타나 불일치로 캐시 무효화가 의도치 않게 동작할 위험성 존재
- 액션
  팩토리 함수 패턴을 적용한 계층적 키 구조 설계
  FSD 아키텍처 구조에서 각 엔티티의 model 디렉토리에 useQuery, useMutation 을 커스텀 훅으로 분리하여 배치
- 결과
  쿼리 키를 단일 파일에서 구조화하여 관리하고, 쿼리 키가 적용되는 커스텀 훅을 도메인 별로 추상화하여 일관성과 확장성을 확보

- 상황
  화면 포커스 변경 등 사소한 이벤트마다 불필요한 API 요청 발생
- 액션
  서비스 체류 시간을 고려한 staleTime, gcTime, refetchOnWindowFocus 설정
  선택적 파라미터가 있는 커스텀 훅 패턴에 enabled 옵션을 적용
- 결과
  동일 데이터를 여러 컴포넌트에서 구독해도 중복 네트워크 요청 없이 캐시를 공유하여 불필요한 API 요청을 감소
  서버 응답 대기 없이 UI 가 즉시 반응하고, 실패 시 자동 롤백되는 낙관적 업데이트를 구현하여 사용자 경험 향상

### 3. 테이블 모델링 및 Supabase 기반 백엔드 구현

- 상황
  개인 프로젝트를 처음 진행하면서 서버리스 백엔드 구축의 필요성을 느낌
  도출된 도메인을 어떻게 구조화하고, 관계를 정의할지 등 문서화에 대한 고민
- 액션
  서비스 기획 단계에서 ERD, 테이블 정의서, 용어 사전을 도입, 서비스 종료시까지 꾸준히 업데이트하여 ‘살아있는 문서’로 활용
  Supabase 기반 9개 테이블 설계 및 외래 키 제약 조건, RLS 설정
  사용자 단위 파일 권한 관리를 위한 Storage 경로 구조(user/{user_id}/profile/{file})와 Policy 설계
- 결과
  개발 과정에서 발생하는 기능 추가나 잦은 스키마 변경 상황에서도 빠르게 판단하고 대응
  초기 설계에 대한 고민과 분석의 중요성을 체감, 서비스 안정성과 확장성의 기반이 된다는 것을 깨달음

### 4. BFF 구조 재설계로 서비스 요구사항 최적화

- 상황
  별도 서버를 구축할 필요가 없는 Vercel Function 을 채택, BFF 를 도입하여 분산되어 있던 API 호출 로직을 통합하여 코드량을 80% 감소

## 문제 해결

### 1. 타입 계층 구조화로 중복 정의 제거 및 확장성 개선

- **문제**: NoSQL API 요청/응답 타입을 정의하는 과정에서 상품 타입별 필드가 Extra 타입에 평탄화된 형태로 누적되며 옵셔널 필드가 급증했고, 그 결과 타입 정의가 중복되고, 요청별 조합이 복잡해졌으며, 수정 시 영향 범위를 예측하기 어려운 문제 발생
- **해결**: TypeScript 의 유틸리티 타입을 활용해 핵심 데이터 타입을 단일 기준 타입으로 재정의하고, 공통 타입을 기반으로 요청 목적별 타입을 파생 생성하도록 계층적 구조로 개선
- **성과**: 타입 중복 정의를 제거해 가독성과 유지보수성 향상, 상품 타입별 필드 접근이 컴파일 타임에 검증되도록 하여 타입 안정성을 확보, 확장성 개선
